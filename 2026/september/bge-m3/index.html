BGE-M3: หนึ่ง encoder สาม retrieval head

สวัสดีครับทุกคน วันนี้ผมอยากชวนมาดูตัวอย่างง่าย ๆ เริ่มจากคำถามที่ว่า “สนามบินสุวรรณภูมิเปิดใช้เมื่อปีใด” กับเอกสาร 2 ชิ้นที่ดูเผิน ๆ ก็น่าจะแยกออกจากกันได้ไม่ยาก

เอกสารแรกคือคำตอบที่ถูกต้อง — “ท่าอากาศยานสุวรรณภูมิเริ่มให้บริการเชิงพาณิชย์ในเดือนกันยายน พ.ศ. 2549” ส่วนเอกสารที่สองพูดถึงสนามบินดอนเมือง — “สนามบินดอนเมืองเป็นสนามบินที่เก่าแก่ที่สุดแห่งหนึ่งในเอเชีย เปิดใช้ในปี พ.ศ. 2457” สังเกตว่าชิ้นหลังมีคำว่า “สนามบิน” “เปิดใช้” และ “ปี” ตรงกับคำถามเป๊ะ แต่เป็นคำตอบที่ผิด

พอเอาไปทดสอบจริงกับ BAAI/bge-m3 (ตัวเลขเต็มอยู่ใน experiments/2026/September/bge-m3/results/thai-demo.json) ผลที่ได้น่าสนใจครับ

  • หัว late interaction ให้คะแนนเอกสารดอนเมืองสูงกว่าคำตอบจริง (0.7196 เทียบกับ 0.7020) เพราะคำที่ตรงกันหลายคำทำให้จับคู่ระดับ token ได้เยอะเกินไป
  • อีกคำถามหนึ่ง “ราคาน้ำมันที่สูงขึ้นทำให้ค่าเดินทางแพงขึ้นหรือไม่” กับเอกสารที่ตอบเรื่องนี้ตรง ๆ แต่ใช้คำว่า “เชื้อเพลิง” กับ “ค่าโดยสาร” หัว lexical ให้คะแนนเพียง 0.0419 คือแทบเป็นศูนย์ และพอคำถามเป็นภาษาไทย (“เมืองหลวงของประเทศญี่ปุ่นคือเมืองอะไร”) แต่เอกสารที่ตอบเป็นภาษาอังกฤษ หัวเดียวกันให้ 0.0000 พอดี จนไปจัดเอกสารดอนเมือง (0.0309) ไว้เหนือคำตอบจริง

หัว dense จัดอันดับถูกทั้งสามข้อ แต่กับคำถามสุวรรณภูมิมันชนะเอกสารดอนเมืองแค่ 0.7100 เทียบ 0.6821 ส่วนอีกสองหัวต่างก็พลาดคนละข้อ พอรวมคะแนนของทั้งสามหัวเข้าด้วยกัน ทั้งสามข้อก็ถูกหมด คำถามของโพสต์นี้จึงไม่ใช่ “โมเดล embedding ตัวไหนดีที่สุด” แต่คือ “ถ้าเราไม่ต้องเลือกแค่ทางใดทางหนึ่งล่ะ”

วันนี้ผมจะพามาแกะเปเปอร์ M3-Embedding (Chen et al., 2024, arXiv:2402.03216) ซึ่งตอบโจทย์นี้ด้วยการให้ encoder ตัวเดียวสร้าง representation 3 แบบพร้อมกันจาก forward pass รอบเดียว แล้วฝึกให้ทั้งสามหัวช่วยกันแทนที่จะแย่งกัน โมเดลที่ปล่อยออกมาคือ BAAI/bge-m3 ที่หลายคนอาจใช้อยู่แล้ว แต่อาจยังไม่รู้ว่าข้างในมีอะไรมากกว่า dense vector

อ่านจบแล้ว สิ่งที่ได้ไม่ใช่แค่ความเข้าใจโมเดลตัวนี้ แต่เป็นสามวิธีค้นหาหลักของโลก information retrieval ที่อธิบายบนตัวอย่างชุดเดียวกัน และช่วงท้ายเราจะมารื้อดูกันว่าทั้งหมดนี้ทำอะไรกับภาษาไทยจริง ๆ ซึ่งเป็นส่วนที่เปเปอร์ไม่ได้วัดไว้

ข้อสรุปที่ตัวเลขรองรับจึงไม่ใช่ “ภาษาไทยแพง” แต่เป็น ภาษาไทยที่เป็นร้อยแก้วธรรมดาราคาพอ ๆ กับอังกฤษ ส่วนที่แพงคือชื่อเฉพาะ วันเดือนปี และตัวเลข ซึ่งบังเอิญเป็นเนื้อหาส่วนใหญ่ของเอกสารราชการ ข่าว และเอกสารกฎหมายไทย เพดาน 8,192 จึงเป็นปัญหาสำหรับ เอกสารบางประเภท ไม่ใช่สำหรับภาษาไทยทั้งภาษา

หัว sparse ให้น้ำหนักอะไรบ้าง

คำถามเดียวกันสองภาษา ฝั่งไทย สนามบิน 0.2462, สุวรรณ 0.2443, ภูมิ 0.2159, เปิด 0.1697, ใช้ 0.1544, เมื่อปี 0.1434, ใด 0.1034 และ token ช่องว่าง ▁ 0.0282 ฝั่งอังกฤษ ▁Su 0.1208, varna 0.2444, bhu 0.2080, mi 0.1388, ▁Airport 0.2375, ▁open 0.1851, ▁year 0.0970 ส่วน ▁which 0.0326, ▁did 0.0397 และ ? 0.0156

อ่านสองแถวนี้คู่กันแล้วเห็นสามอย่าง

  • หัว sparse ทำงานเหมือนกันทั้งสองภาษา คือกดน้ำหนักคำหน้าที่ (▁which, ▁did, ?, ใด) และดันน้ำหนักคำเนื้อหา ไม่มีสัญญาณว่ามันสับสนกับภาษาไทยเป็นพิเศษ
  • ชื่อเฉพาะถูกซอยทั้งสองภาษา “สุวรรณภูมิ” เป็น สุวรรณ|ภูมิ ส่วน “Suvarnabhumi” เป็น ▁Su|varna|bhu|mi และในทั้งสองภาษาน้ำหนักไปกองที่ชิ้นที่จำเพาะที่สุด (สุวรรณ 0.2443, varna 0.2444 — ใกล้กันจนน่าสนใจ) ไม่ใช่ที่ชิ้นที่พบทั่วไป (mi 0.1388)
  • token ช่องว่าง ▁ ในฝั่งไทยได้น้ำหนัก 0.0282 ไม่ใช่ศูนย์ แปลว่ามันเข้าไปอยู่ใน inverted index ด้วย และไปตรงกับ ▁ ของทุกเอกสารในคลัง ดูใน thai-demo.json จะเห็นว่ามันมีส่วนร่วมในคะแนน sparse ของคู่ q2/p2 จริง (0.0283 × 0.0536 = 0.0015 — ตัวเลขชุดนั้นมาจากคนละรัน จึงต่างจากรูปข้างบนที่ทศนิยมหลักสุดท้าย) เล็กมากเมื่อเทียบกับ สุวรรณ (0.0675) แต่มันคือ term ที่ไม่มีความหมายซึ่งตรงกันเสมอ

แล้วมันช่วยหรือมันพัง

คำถามที่ควรถามคือ lexical matching บน subword ที่ไม่ตรงขอบเขตคำ — มันช่วยหรือมันพัง ตอบตรง ๆ ว่า ยังตอบไม่ได้จากข้อมูลชุดนี้ และนี่คือสิ่งที่ควรพูดให้ชัดแทนที่จะเดา

ฝั่งที่บอกว่าช่วย: subword matching ไม่ต้องพึ่งตัวตัดคำไทยที่ถูกต้อง ระบบที่ใช้ BM25 กับ newmm จะพังทันทีเมื่อตัดคำผิด ส่วน BGE-M3 ไม่มีขั้นนั้นให้พัง และตัวเลขในเปเปอร์ก็หนุนอยู่ — Sparse ชนะ BM25 ทุกภาษาบน MIRACL (Table 1) รวมทั้งไทย (70.9 เทียบ 49.1)

ฝั่งที่บอกว่าพัง: token ที่คร่อมคำอย่าง ของประเทศ และ token ช่องว่างที่ได้น้ำหนักไม่เป็นศูนย์ คือ term ที่ match ได้โดยไม่มีความหมาย บนคลังใหญ่ ๆ ของแบบนี้กินแบนด์วิดท์ของ posting list และดัน precision ลง — แต่ “บนคลังใหญ่ ๆ” คือสิ่งที่หกประโยคบอกไม่ได้

สิ่งที่ขาดคือชุด eval ภาษาไทยที่วัดได้จริง MIRACL-th มีอยู่แต่อยู่ในข้อมูล fine-tuning ของ M3 เอง (ผ่าน Mr. TyDi และ MIRACL train) ผลบน dev set จึงเป็นการวัด in-domain ส่วน MLDR-th มาจาก mC4 ล้วนและยาวเฉลี่ยเกือบ 8,192 token ซึ่งไม่ได้แทนเอกสารไทยทั่วไป นี่คือช่องว่างที่โพสต์เดือนตุลาคมและพฤศจิกายนจะไปแก้

เราลองผสมน้ำหนักของสามหัวเองได้ข้างล่างนี้ เลือกคำถาม ลากน้ำหนักหรือเลือกชุดน้ำหนักที่เปเปอร์ใช้ แล้วดูว่าคำตอบที่ถูกยังอยู่บนสุดหรือไม่

ไฟล์เดียวกันยังเก็บระดับ token ไว้ให้ดูกลไกของแต่ละหัว: outputs.lexical_intersection คือชิ้นคำร่วมกับผลคูณน้ำหนัก (ผลรวมตรงกับคะแนน sparse), outputs.token_level คือตาราง cosine ระหว่าง token ของ query กับ passage พร้อม max ต่อแถวและค่าเฉลี่ย (ตรงกับคะแนน multi-vector) และ outputs.dense_head8 คือ 8 มิติแรกของเวกเตอร์ dense

วิดเจ็ตนี้ให้เราเดิน MaxSim ทีละชิ้นคำของคำถาม แล้ววางผลคูณน้ำหนักของหัว sparse บนคู่เดียวกันไว้ข้าง ๆ

แล้วปี 2026 ยังควรใช้ไหม

เปเปอร์เป็นฉบับ ก.พ. 2024 (ฉบับที่อ่านคือ v5, ธ.ค. 2025) และ leaderboard ขยับไปแล้ว ทิศทางที่ชัดที่สุดคือ embedder ที่ใช้ decoder-only LLM เป็น backbone แทน encoder-only รุ่นเดิม

ปิดท้าย

สิ่งที่ควรได้กลับไปไม่ใช่ “BGE-M3 ดีหรือไม่ดี” แต่เป็นสามวิธีจับคู่ query กับเอกสารที่เห็นทำงานพร้อมกันในโมเดลเดียว: lexical ที่นับ term ร่วมและเป็นศูนย์พอดีเมื่อไม่มีอะไรร่วม, dense ที่บีบทุกอย่างลงเวกเตอร์เดียวและข้ามภาษาได้, และ late interaction ที่จับคู่ทีละ token แล้วบางครั้งก็ถูกคำที่ตรงกันหลอกเอา สามอย่างนี้จะกลับมาอีกในทุกโพสต์ของซีรีส์นี้

โค้ดและตัวเลขทั้งหมดรันซ้ำได้: experiments/2026/September/bge-m3/ มีสองสคริปต์ (run_bge_m3.py สำหรับกริดสามหัว, run_tokenizer_thai.py สำหรับส่วน tokenizer) และ make_figures.py ที่วาดสองรูปสุดท้ายจาก JSON โดยไม่มีตัวเลขเขียนมือ

คำถามที่ค้างไว้ในหัวข้อ “แล้วมันช่วยหรือมันพัง” ต้องการเครื่องมือที่ยังไม่มี โพสต์หน้า (ตุลาคม) จึงเป็นเรื่อง ทำไม BM25 พังกับภาษาไทย — ว่าด้วย tokenizer ในฐานะ hyperparameter ของ retrieval ไม่ใช่ขั้น preprocessing
